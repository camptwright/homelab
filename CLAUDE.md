# CLAUDE.md - homelab

## What This Repo Is

Infrastructure-as-config for Camp's homelab. It defines the Docker Compose stack running in the `docker-core` LXC (CT 110) on a single Proxmox node, the KAMRUI Pinova P1 (AMD R2544, 2 cores, 16GB RAM, 256GB SSD). This is an operations repo: compose files, service configs, runbooks, and Claude Code prompt sequences. Application code lives elsewhere (see Related Repos).

Domain: **camptwright.com**, DNS on Cloudflare. Public entry is exclusively via a named Cloudflare tunnel (`kamrui`); admin surfaces sit behind Cloudflare Access restricted to one email. There is no port forwarding and never will be.

## Architecture Rules (do not violate)

1. **Profiles are the deployment unit.** `core` (postgres, redis, litellm, cloudflared, ntfy, ollama-embed), `apps` (dashboard, miniflux, uptime-kuma, linkding, beszel + agent), `adjutant`, `extras`, `media` (future, wrong host: Jellyfin belongs on a future Intel node with Quick Sync, not this AMD box). `COMPOSE_PROFILES=core,apps` is set in .env; always pass or export profiles such that dependencies are in scope, or compose fails with "depends on undefined service".
2. **One shared Postgres** (pgvector/pgvector:pg16) serves adjutant, dashboard, and miniflux as separate databases/users. New services get a new database + user added to postgres-init.sql AND a matching ALTER USER line in SETUP.md A5. No service gets the postgres superuser.
3. **Every service has a mem_limit.** The host has 16GB shared with the Proxmox host and three other LXCs (wedding platform, Fantasy Edge, Los Ebanitos). The RAM budget table in SETUP.md is the ledger; update it when adding services. If a new service pushes the docker-core total past ~10GB steady-state, something else moves or the service waits for the cluster.
4. **All LLM traffic goes through LiteLLM** (`http://litellm:4000/v1` in-network, `http://<lxc-ip>:4000/v1` from other LXCs like OpenClaw). Services reference aliases (fast/worker/planner/embed), never provider model names or API keys. The GPU-node cutover must remain a litellm-config.yaml-only change.
5. **Access covers admin surfaces only.** In Access: admin, rss, status, links, beszel. Deliberately NOT in Access: ntfy (its phone app cannot complete a browser login; it uses its own deny-all + user auth) and any public site (wedding, Los Ebanitos). When adding a tunnel hostname, decide which bucket it belongs to and add it to the Access app if admin.
6. **Secrets live in .env only.** Anything committed must reference `${VARS}`. New variables get a documented line in .env.example.
7. **cloudflared reaches services by compose service name** (e.g. `uptime-kuma:3001`). Tunnel public-hostname URLs must not include a scheme prefix in the URL field (the Type dropdown supplies it) and must match compose service names exactly.

## Operational Lessons (learned the hard way; keep true)

- `beszel-agent` uses `network_mode: host` and therefore cannot inherit the `&small` anchor (which sets `networks:`). It is written out longhand. Do not "clean this up".
- Postgres healthcheck has `start_period: 90s` because first init on 2 cores exceeds the default budget. Keep it.
- The A5 password rotation requires `source .env` in the same shell first; running the ALTER USER block with unset vars CLEARS the passwords (postgres treats empty string as "remove password"). The runbook's echo sanity check exists for this reason.
- `wellthread-web` is the sole service in profile `pending`: its GHCR package does not exist or is not anonymously pullable. The dashboard, Marketdesk, and Adjutant packages are public, digest-pinned, and live. Do not move Wellthread web to `apps` until its source-SHA image can be pinned and pulled.
- Wiping `homelab_pgdata` is the correct fix for a failed FIRST init only. Once real data exists, never suggest volume removal as a fix; restore from the nightly pg_dumpall instead.
- **`net0` must be `ip6=auto`, never `ip6=dhcp`.** With `ip6=dhcp`, `ifup` blocks on a DHCPv6 Solicit that nothing on this LAN answers; `networking.service` hits its start timeout, is killed, and eth0 never gets its **IPv4** lease either. Symptom: `ip route` shows only the docker bridges, `ping` says "Network is unreachable", and every container logs `[Errno -3] Temporary failure in name resolution`. Fix: `pct set 110 -net0 ...,ip6=auto,...` then `systemctl restart networking` (Proxmox rewrites `/etc/network/interfaces` on config change).
- **Docker is nested in an unprivileged LXC, so the cgroup OOM event never reaches Docker.** A memory-killed container reports `OOMKilled=false`, and `docker inspect` can even show `ExitCode=0` because it races the restart. The only reliable signal is running the service in the foreground (`docker compose up <svc>`, no `-d`) and reading the real exit code: **137 = 128+9 = SIGKILL = out of memory**. Do not trust the `OOMKilled` flag on this host.
- LiteLLM needs ~1.07GB steady-state to hold six models plus the router, so its `mem_limit` is 1536m. At 512m it SIGKILLed mid-startup and crash-looped (6353 restarts) while logging nothing.
- **Editing `.env` does not affect running containers.** Compose injects environment at container *creation*; a service started before a value was filled in keeps the old (often empty) value forever. Miniflux crash-looped on `password authentication failed` while `psql` with the same credentials succeeded, because its container had an empty password baked in. Fix: `docker compose --profile core --profile apps up -d --force-recreate <svc>`.
- **`--force-recreate` doesn't fix this for apps whose credentials live in a persistent data volume, not just the container.** Linkding's `LD_SUPERUSER_PASSWORD` only seeds the `camp` superuser the *first* time its SQLite volume initializes; recreating the container with a new `.env` value does nothing because the account already exists from an earlier init and the app never re-syncs it. Symptom: correct-looking credentials still fail login, container logs show nothing but healthy `/health` checks (no auth errors at all, since the app never even sees a request worth logging as a failure until you actually try). Diagnose by comparing the volume's creation date (`docker volume inspect homelab_linkding --format '{{.CreatedAt}}'`) against the container's (`docker inspect ... --format '{{.Created}}'`) — if the volume predates the container, the stored account is stale relative to `.env`. Fix: reset the password directly against the app's own auth store, e.g. for a Django app, `docker compose exec linkding python manage.py shell -c "from django.contrib.auth.models import User; u = User.objects.get(username='camp'); u.set_password('...'); u.save()"` rather than trusting env vars to reach an already-initialized volume.
- **nginx resolves `proxy_pass` hostnames at startup and dies if one is missing** (`[emerg] host not found in upstream`). One stopped backend therefore takes the entire gateway offline, including routes that had nothing to do with it. Reference every upstream through a variable plus `resolver 127.0.0.11` (Docker's embedded DNS) so resolution happens per-request and a missing backend degrades to a 502. Note `proxy_pass $var` does not append the request URI - use `$var$request_uri`, or `rewrite ... break` to reproduce trailing-slash prefix stripping.
- **Editing a bind-mounted config does not restart the container.** `docker compose up -d` sees no change to the service definition and does nothing; the old config keeps serving. Use `docker compose restart <svc>` after editing anything mounted in.
- **PostgREST caches the schema at startup.** Apply migrations to `wellthread` and it will keep serving the old cache - new tables 404 on write while oddly returning 200 on read. Always follow a migration with `psql -d wellthread -c "NOTIFY pgrst, 'reload schema'"` and confirm the log line reports the expected relation count.
- **`postgres-init.sql` only runs on an EMPTY volume.** Anything added to it after the cluster exists must ALSO be applied by hand to the live instance, or it silently never happens. Wellthread's roles were added that way on 2026-08-02.
- `docker compose exec -T` **consumes stdin**. Inside a piped script (`ssh host 'bash -s' < script`) it silently swallows the rest of the script. Always append `</dev/null` to `exec`/`run` calls in remote runbook scripts.
- **`beszel-agent`'s `KEY` env var needs an actual SSH public key, not the system's UUID/token from the hub UI.** A misconfigured `BESZEL_AGENT_KEY` (36 chars, looked like a UUID) crash-looped the agent every ~14-60s with `Failed to load public keys: ... error: ssh: no key found` while the hub itself (`beszel` service) stayed healthy - only the agent crashed, easy to miss since it doesn't announce itself on the dashboard. The hub persists its own keypair in its named volume (`docker volume inspect homelab_beszel --format {{.Mountpoint}}`, then `.../id_ed25519` - no shell in the hub image, but `ssh-keygen -y -f id_ed25519` derives the public key from it directly without needing the web UI at all). Set `BESZEL_AGENT_KEY` to that derived public key, then `--force-recreate` the agent.
- **The dashboard's Drizzle schema can exist in the repo with zero tables ever created in the deployed database.** `npm run db:migrate` requires a separate Docker build target (`docker build --target migrator`, see the Dockerfile) that isn't part of the normal deploy - if nobody ever runs it, every DB-backed tile (articles, finance, school) fails on a missing-relation error while looking merely "empty." Confirmed via `\dt` inside `postgres` showing zero relations for the `dashboard` database despite the app running "healthy" for weeks. Fix: build the `migrator` target and run it once with `DATABASE_URL` pointed at the real `postgres` service - `docker build --target migrator -t dashboard-migrator . && docker run --rm --network homelab_homelab -e DATABASE_URL=... dashboard-migrator`.
- **Uptime Kuma's `/api/*` router has no general "list monitors + status" REST endpoint at all**, despite having an `api_key` table that looks like it should back one - that table backs Socket.IO auth and a couple of internal checks, not a documented REST surface. Confirmed by reading `server/routers/api-router.js` directly: it's almost entirely SVG badge generators (`/api/badge/:id/status` etc, each requiring the monitor to already be in a *public* status-page group) plus the push-monitor endpoint. The one JSON API actually meant for "read monitor status from another app" is the **public status page API** - `/api/status-page/:slug` (config + monitor list) and `/api/status-page/heartbeat/:slug` (recent heartbeats per monitor, latest entry = current status) - no auth at all, by design, since status pages are meant to be publicly embeddable. Set one up once (a `status_page` row, a `public=1` `group` row linked to it, `monitor_group` rows for each monitor you want exposed) and every consumer reads the same public JSON. The dashboard's System tile uses slug `dashboard-internal` for exactly this.
- **Beszel's dashboard integration needs a dedicated service-account superuser, not the personal login.** Beszel (PocketBase-based) gates its `systems` collection behind auth with no read-only/API-key concept - only superusers or app-level users. Created one via the hub's own CLI rather than touching anyone's personal credentials: `docker compose exec beszel /beszel superuser upsert dashboard-api@internal.local '<password>'`, then authenticate with `POST /api/collections/_superusers/auth-with-password` to get a token for `/api/collections/systems/records`.
- **A Docker socket mounted `:ro` is not a read-only Docker API.** Beszel's agent can ask the daemon to create privileged containers, mount host paths, or inspect other containers regardless of the socket inode's mount mode. Treat the pinned agent image as root-equivalent trusted code; `SECURITY.md` records why that risk is accepted and what the surrounding controls do and do not contain.

## Conventions for Changes

- Compose edits: keep the `&small` anchor pattern, profiles, and mem_limits. Validate before handing back: the file must parse (`docker compose config`) with core+apps profiles active.
- Runbook edits: SETUP.md is written as numbered, copy-pasteable steps with verification after every stage. Match that style. When a step has a failure mode we have hit, document the symptom and fix inline.
- New services: add to docker-compose.yml (right profile, mem_limit, logging via the anchor), .env.example if configurable, a tunnel hostname + Access decision per rule 5, an Uptime Kuma monitor note in SETUP.md, and the RAM ledger.
- Never add: port forwarding, host-network services (beszel-agent is the one exception), services storing secrets in images, or anything that bypasses LiteLLM for LLM calls.
